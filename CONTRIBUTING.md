# Contributing to peculiar-ui

Thank you for your interest in contributing to `peculiar-ui`! This document describes how to set up the project, which checks a change must pass, and how releases are made.

## Development Setup

### Prerequisites

- Node.js `^20.19.0 || >=22.12.0` (CI uses Node.js 24)
- npm (the repository is an npm workspace locked with `package-lock.json`)

### Installation

```bash
git clone https://github.com/PeculiarVentures/peculiar-ui.git
cd peculiar-ui
npm ci
npm test
```

`npm ci` also builds both packages (`prepare`), which Storybook needs.

## Project Layout

- `packages/react-components/` is `@peculiar/react-components`: the components, hooks and theme, plus their Storybook stories (`*.stories.tsx`, `*.mdx`) and the Storybook config in `.storybook/`.
- `packages/color/` is `@peculiar/color`, the color conversion and palette helpers the theme is built on.
- `packages/<name>/src/index.ts` is each package's only public entry point and must stay aligned with its `exports`.
- `tsdown.config.ts` at the repository root builds both packages (tsdown `workspace` mode). There are no per-package build configs.
- `tsconfig.json` at the root is used for typechecking (sources, tests, stories and configs) and the declaration build. Its `paths` map `@peculiar/color` to `packages/color/src`, so the components and their tests use the color sources without building them first.
- `vitest.config.ts` at the root runs both packages' tests as two Vitest projects (`color` in Node, `react-components` in jsdom with `packages/react-components/vitest.setup.ts`).
- `packages/<name>/build/` is generated by `npm run build` and is not committed. `packages/react-components/public/` is the generated Storybook site.

## Development Workflow

### Storybook

```bash
npm run dev  # Storybook at http://localhost:3000
```

`npm run --workspace @peculiar/react-components build:storybook` builds the static site into `packages/react-components/public/`; the Release workflow deploys it to [GitHub Pages](https://peculiarventures.github.io/peculiar-ui/) on every push to `main`. Add or update the stories of every component you change.

### Code Quality

Before opening a pull request, run from the repository root:

```bash
npm run lint          # oxlint
npm run format:check  # oxfmt
npm run typecheck     # tsc
npm test              # vitest, runs once and exits
npm run build         # tsdown, also checks both packages with attw
```

Fix lint and formatting issues with `npm run lint:fix` and `npm run format`. Use `npm run coverage` to produce a coverage report, and `npx vitest run packages/react-components/src/Button` to run some of the tests.

### Testing

- Use Vitest: import `describe`, `it` and `expect` from `vitest` (globals are off).
- Put tests next to the code they cover as `*.test.ts(x)`. Component tests use `@testing-library/react` and snapshots serialized with `@emotion/jest`, so the snapshots include the generated styles; update them with `npx vitest run -u` and review the diff.
- CI runs the tests on React 18 (the `devDependencies`) and on React 19. Check both when you touch refs, effects or rendering: `npm install --no-save react@19 react-dom@19 @types/react@19 @types/react-dom@19`, run `npm run typecheck` and `npm test`, then `npm ci` to go back.
- Keep tests deterministic: no wall-clock time, randomness, network access or external services.

### Build And Package Exports

Both packages are ESM-only; there is no CommonJS build, and CommonJS consumers load them through `require(esm)`. tsdown builds `src/index.ts` into `build/index.js` with `.d.ts` declarations. Output is unbundled: every source module is emitted under `build/` mirroring `src/`, but only the root entry is reachable through `exports`. The syntax target comes from `engines.node`; do not set `target` in `tsdown.config.ts`. JSX uses the automatic runtime (`react/jsx-runtime`).

`exports` and the legacy `main`/`module`/`types` fields in each `packages/<name>/package.json` are generated by tsdown on every build and must not be edited by hand. CI fails if the build changes a tracked file.

Use named exports only (no `export default`) and no top-level `await`, so `require()` of the packages keeps working on supported Node.js versions. Use `import type` for type-only imports (`verbatimModuleSyntax`).

Both packages have `"sideEffects": false`, so bundlers drop the modules an app doesn't import. Don't add code that only works because a module was imported for its side effects (global styles belong in `ThemeProvider`, not at module level).

Start every module that uses React or emotion at runtime (components, hooks, contexts, providers) with `'use client'`, so Next.js App Router Server Components can import it. Modules with only types, theme objects or plain helpers (`styles/default_theme.ts`, `styles/foundations/*`, `styles/utils.ts`, `utils/*`) stay without it.

### Dependencies

- `react`, `react-dom` and `@types/react` (optional) are **peer** dependencies (`^18.0.0 || ^19.0.0`); the root `devDependencies` hold the React 18 versions used for development.
- `@emotion/*` stay regular `dependencies` with caret ranges, so npm dedupes them with the app's copy: the components read the theme and style cache from emotion's contexts.
- Declare every package that `src/` imports, including types that end up in the published `.d.ts` (`csstype`, `@types/react-transition-group`). Don't rely on hoisting.
- The internal `@peculiar/color` range is bumped by the release pull request; don't change it by hand.

### Commit Messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Pull requests are squash-merged, so the pull request title becomes the commit message and must follow the same format.

```plain
type(scope): description

[optional body]

[optional footer]
```

Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `style`, `revert`. Use the component or package as the scope for targeted changes (for example `fix(tooltip): ...`, `feat(color): ...`).

Mark breaking changes with `!` after the type or scope (for example `feat(select)!: ...`) and/or a `BREAKING CHANGE:` footer. Dependabot titles its pull requests `chore(deps)`; retitle a runtime dependency bump that users need to `fix(deps):` or `build(deps):` before merging, or it won't be released.

### Pull Requests

1. Fork the repository and create a branch from `main`.
2. Make your changes, with tests and stories.
3. Run the checks listed above.
4. Open a pull request with a Conventional Commit title.

## Code Style

- Write TypeScript.
- Follow the oxlint (`.oxlintrc.json`) and oxfmt (`.oxfmtrc.json`) configuration.
- Keep changes small and localized to the owning component or package.
- Keep public exports stable; breaking changes need a major release.

## Releases

Releases are managed by [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`). Both packages share one version and are released together. Do not push version bumps or release tags to `main` by hand.

1. On every push to `main`, the **Release** workflow (`.github/workflows/publish.yaml`) first runs lint, format, typecheck, tests, build and the Storybook build (the **Test** workflow), then deploys Storybook to `gh-pages`. Only when the checks pass does release-please open or update a `chore(release): vX.Y.Z` pull request. It bumps the root and both `packages/*/package.json` versions, the `@peculiar/color` range in `@peculiar/react-components`, and `package-lock.json`. The version comes from the commits: a breaking change bumps major, `feat` bumps minor, and `fix`, `perf`, `build`, and `revert` bump patch. Other types do not trigger a release.
2. Merge the release pull request. release-please creates the `vX.Y.Z` tag and the GitHub Release with the notes from the pull request; the workflow then publishes every package whose version is not on npm yet via Trusted Publisher, with provenance, `@peculiar/color` before `@peculiar/react-components`.

To retry a failed or partial npm publish, run **Release** manually from the `vX.Y.Z` tag, or from `main` as long as nothing under `packages/` has changed since that tag; packages already on npm are skipped. Set the optional `RELEASE_TOKEN` secret (PAT or GitHub App token) so the Test workflow runs on the release pull request. Both packages need an npm Trusted Publisher for this repository, workflow `publish.yaml` and environment `npm`.

Release notes live only in [GitHub Releases](https://github.com/PeculiarVentures/peculiar-ui/releases); there is no `CHANGELOG.md`. Pull requests are squash-merged, so the pull request title must be a [Conventional Commit](https://www.conventionalcommits.org/en/v1.0.0/). Force a version with a `Release-As: x.y.z` line in a commit body. To fix the notes for a merged change, add a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block with the corrected commit message to that pull request's description; edits to the release pull request description are overwritten when new commits land.

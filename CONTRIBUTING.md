## Release Publishing

Releases are managed by [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`). Both packages share one version and are released together. Do not push version bumps or release tags to `main` by hand.

1. On every push to `main`, the **Release** workflow (`.github/workflows/publish.yaml`) first runs lint, format, typecheck, tests, build and the Storybook build (the **Test** workflow), then deploys Storybook to `gh-pages`. Only when the checks pass does release-please open or update a `chore(release): vX.Y.Z` pull request. It bumps the root and both `packages/*/package.json` versions, the `@peculiar/color` range in `@peculiar/react-components`, and `package-lock.json`. The version comes from the commits: a breaking change bumps major, `feat` bumps minor, and `fix`, `perf`, `build`, and `revert` bump patch. Other types do not trigger a release.
2. Merge the release pull request. release-please creates the `vX.Y.Z` tag and the GitHub Release with the notes from the pull request; the workflow then publishes every package whose version is not on npm yet via Trusted Publisher, with provenance, `@peculiar/color` before `@peculiar/react-components`.

To retry a failed or partial npm publish, run **Release** manually from the `vX.Y.Z` tag, or from `main` as long as nothing under `packages/` has changed since that tag; packages already on npm are skipped. Set the optional `RELEASE_TOKEN` secret (PAT or GitHub App token) so the Test workflow runs on the release pull request. Both packages need an npm Trusted Publisher for this repository, workflow `publish.yaml` and environment `npm`.

Release notes live only in [GitHub Releases](https://github.com/PeculiarVentures/peculiar-ui/releases); there is no `CHANGELOG.md`. Pull requests are squash-merged, so the pull request title must be a [Conventional Commit](https://www.conventionalcommits.org/en/v1.0.0/). Force a version with a `Release-As: x.y.z` line in a commit body. To fix the notes for a merged change, add a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block with the corrected commit message to that pull request's description; edits to the release pull request description are overwritten when new commits land.
